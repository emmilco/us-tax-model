## Ground rules I applied

- **Lines marked "(gate)" are observed.** Only "(helper)" is unobserved, so `person.edu_over_refused` counts as a printed line.
- **I can only see the listed definitions.** "Only reader" premises are checked against this list and nothing more. Several expressions are cut off, and many referenced lines are not defined here, including `share_raw`, `f7206_min`, `eic.eligible` and `person.age65`.

## C1: EQUIVALENT (given premises)

- `has_taxable` true means `line16` is known and greater than `sales.zero`. That requires:
  - the `unsupported` gate is false (otherwise `line16` is a refusal, and so is `gt`), and
  - `line16`'s choose took a real branch.
- The `has_dist=false` branch gives `zero`, which is not greater than `sales.zero`. So `line16` must equal `line16_figured`, and the mutant `subject` has the identical value.
- If `has_taxable` is not true, `line17b_figured` is never read.
- **Premises:**
  - `sales.zero` = 0 and `f8889.zero` = 0. If `sales.zero` were negative, the zero branch could pass.
  - No reader of `subject` exists besides `line17b_figured`.

## C2: EQUIVALENT (given premises)

- With `use_last_month` true and `dec_coverage` = self_only, the inner `any` of `married_family` comes out false:
  - Disjunct 1 is `all[true, false]`, which is false.
  - Disjunct 2's first conjunct (`use_last_month == false`) is false. That decides it before the `months_fa…` comparison.
- So `married_family` is false, or it is a refusal from `household.married` that is identical in both versions. Then `split` is false or that same refusal, and `line6` never reads `line6_split`.
- **Premises I cannot check:**
  - `married_family` is truncated. The `any` may have more disjuncts, and the outer `all` may have more conjuncts.
  - Nothing other than `self_in_family`, `step4_total`, `step4` and `line6_split` reads these lines.

## C3: EQUIVALENT (given premises), but the claim's justification is incomplete

- This mutation fires whenever `use_last_month` is true, not only when `dec_coverage` = self_only.
- `use_last_month` true requires `dec_coverage` known and not `none`. That leaves two cases:
  - **family:** the original reads `self_dec_year`, which is `self_year`. The mutant reads `self_all`, which is also `self_year` because `use_last_month` is true. Same memoized value.
  - **self_only:** masked exactly as in C2.
- **Premises:**
  - The enum has only family, self_only and none. With a fourth value, `self_dec_year` would have no true guard, and that behaviour is unspecified.
  - The same truncation caveat as C2 applies.

## C4: NOT ESTABLISHED; likely NOT EQUIVALENT

The handling of incomplete values is correct:

| `share` | `self_year` | Result |
|---|---|---|
| refused | anything | `sum` stops at `share` first in both versions |
| unknown | refused | both give `self_year`'s refusal |
| any other incomplete combination | | both give the same unknown |

The known case rests on an unsupported premise:

- With both known, the baseline `step4_total` is 0 and the mutant's is `floor0(share − self_year)`.
- The claim needs `share ≤ step1 ≤ self_year`. Nothing given defines `share_raw` or the `allocation_bad` condition, and nothing ties `step1` (`step1_line3 − line4`) to `self_year` (`self_amount × 12`).
- On the real form, line 3 under the last-month rule is the family limit, which can exceed a self-only annual amount. So the premise looks false.
- **Witness** (if share > self_year):
  - Inputs: `household.married` = true, `hsa_both` = true, `use_last_month` true, `dec_coverage` = family, `share` = 4000, `self_year` = 3000.
  - Baseline: `step4_total` = 0, so `line6` = 4000.
  - Mutant: `step4_total` = 1000, so `line6` = 4000 + 1000 × `hsa.twelfth` ≈ 4083.

## C6: EQUIVALENT

- `itemizes` known false means:
  - every disjunct was evaluated,
  - no unknown was remembered, and
  - no refusal occurred.
- So `mfs_spouse_itemizes` is known false, and `standard` is known (`gt` passes along any incomplete operand).
- A known `standard` means both of its gates were false and it took the branch whose value is `standardraw`. The two values are the same.

## C7: EQUIVALENT (given premises)

- In `itemizes`, with `mfs_spouse_itemizes` true, the second disjunct decides true whatever the first disjunct is:
  - If the first is true, it decides on its own.
  - If the first is unknown, it is remembered, and the deciding true still ends the test.
  - If the first is a refusal, that ends the test before `standard` is read.
- The "cannot refuse" premise is therefore unnecessary.
- `deduction` takes `line17`, and its alternative 1 is never evaluated.
- **Premise:** no other reader of `sa.standard` exists. A Form 1040 line 12 that reads it directly is plausible.

- **Mutant:** `line5_blank = lt(unknown, threshold)` is unknown, so `after_line4` is unknown and `credit` is unknown. Unknown is not R.

Two more weak points:

  - the mutant gives `smaller(unknown, 0)`, which is unknown,

Things I cannot check:

## C10: EQUIVALENT only under unchecked premises

The argument holds if:

1. Exactly one roster entry has role taxpayer. Otherwise `age65` and `work_ssn` could be true on different taxpayer entries, `senior_count` could be 0, and the mutant would print `line35_calc` where the baseline prints 0.
2. `person.age65` and `person.work_ssn` cannot refuse.
   - A spouse entry's refused `age65` is skipped by the taxpayer-filtered counts, because `role == taxpayer` is false and decides first.
   - It is still read by `senior_count`.
   - If `sum_over` propagates refusals, `part5` and therefore `line35` become refusals, while the mutant's `line35_calc` may be known.
   - The `sum_over` refusal semantics are not given.
3. An unknown entry still yields a lower bound of 1 whatever the entry order. Section 4.7.5 does not describe how lower bounds accumulate.
