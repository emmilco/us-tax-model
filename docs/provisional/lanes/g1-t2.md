  `ever_married`, `parents_apart`, `own_money`, `self_support_view`, `citizen_ssn`, `supported_view`, and `dc_paid`,

- **T-270.** `dependent.part_year_home` (months over 6; no generated dependent was born, died or placed in 2025) and
  `dependent.dc_over12_care` (disabled and with you all year) are given on every dependent.
- **BUG-0602, the derived stream.** `derivedStream(stream, salt)` hashes a seed drawn by fast-check (`Spec.stream`,
  `fc.noBias(fc.nat(...))`, the last field of the record), not the inputs. fast-check gives each run a fresh clone of
  the jumped generator (`tossNext`, `Random` clones its source), so a field added last leaves every earlier draw of the
  return as it was. An added root input still moves the fast-check stream (one draw per declared input), as the T-276
  catalog (6.2c) says; that larger change is not made.
- **Inventory 2.6** is already done on this tree: `compare.ts` takes its returns from `corpusReturns` (T-271,

## 3. interview-rules (`engine/src/interview-rules.ts`): BUG-0602 widening and T-290

- **Complete returns selected.** Each profile's generated returns come from a pool (`INTERVIEW_RULES_POOL`, 2,000,
  seed 11): the first `GENERATED` (12, as before, and as interview-length still walks) whatever their status, then
  complete ones until `INTERVIEW_RULES_COMPLETE` (60) complete returns are walked. Statuses are taken by the workers a
  chunk at a time. On this tree: full, 70 returns of the first 326; New York, 71 of the first 1,424 (the New York
  generated returns had no complete one before).
- **Minimal returns with one entry per collection.** The closed full return's rosters, each given one entry alone
  (a roster with fixed choices takes its first one-entry choice, so `$f1095a` gets `form_1` and `$f8889` `hsa`), every
  roster nested under that entry one entry, every answer closed; each must complete, is classed, and is answered in
  `RANDOM_SEEDS` random orders. Nine rosters: `$dependent`, `$f1095a`, `$f8889`, `$interest`, `$oi8z`,
  `$retirement`, `$sales`, `$sc`, `$w2`.
- **T-290, stability.** A random traversal answers the open question of least `stableRank(seed, key)`; the shuffled
  replay sorts by it and a random subset keeps an answer by it. Adding, removing or renaming a question leaves the
  order among the others as it was. The self-test checks that over 30 seeds (an added question, a removed one, the
  shuffled order). With the derived stream fixed, a rename no longer redraws any generated return; an added input
  still shifts the fast-check sample (see section 1).

**Findings of the widened check** (held in `tools/interview_rules_baseline.json` with reasons; the family rewrites
wait for lane T3):

- Early completion (3): `dependent.absence_no_return` (generated.53), `dependent.spouse_relative` (ny.generated.431),
  `sa.elect_itemize` (generated.71). Each probed at the exact random order (`/tmp/t2work/probe.mjs`): either answer
  to the open question leaves the status complete and every target value the same. None can refuse the return.
- Reached only out of bank order (8): `dependent.absence_no_return`, `dependent.edu_tin_issued`,
  `dependent.gross_income`, `dependent.lawful`, `dependent.parent_home_paid`, `dependent.spouse_relative`,
  `person.tin`, `retirement.exception`. Causes not traced here; six are in the T-276 catalog, `dependent.spouse_relative`
  and the out-of-order form of `dependent.lawful` are not.
- Asked and unread: none.
